# 構成リファクタリング案

## 目的

既存の機能仕様と通常時の動作を維持しながら、責務の分離、テスト容易性、起動時の安全性を改善する。

## 現状の課題

- `main.py`が設定、外部API通信、日記処理、リンク警告、定期実行、Discordイベント、Webサーバー起動を担当している。
- import時に環境変数の読み込み、Webサーバー起動、Bot起動が発生していた。
- 設定値がモジュール変数として分散していた。
- Discord通知処理と各ジョブの処理が密結合している。
- 定期実行ループに同じ構造の処理が重複している。
- `web_server.py`がFlaskアプリ、ルート登録、Webサーバー起動を兼ねている。

## 実施順序

### 1. `main.py`の起動副作用を除去する

`main()`を起動入口とし、import時にはWebサーバーやBotを起動しない。

### 2. 設定を`AppConfig`へ集約する

環境変数の読み込み、既定値、形式検証、リンク警告しきい値の補正を設定モジュールへ集約する。

### 3. 日記処理を分離する

テンプレート展開、日記ページ作成、更新確認、日記用Cosense通信を`diary/`へ移す。

### 4. Discord通知を共通化する

チャンネル取得、メッセージ長制限、メンション、送信失敗処理を通知コンポーネントへ移す。

### 5. 定期実行ループを整理する

指定時刻実行と一定間隔実行を共通の実行制御へ整理する。ただし、実行間隔の違いは維持する。

### 6. Webアプリをアプリファクトリ化する

Flaskアプリ生成とルート登録を関数化し、テスト時に設定と依存サービスを差し替えられるようにする。

### 7. HTTPクライアントのセッション共有を検討する

外部APIクライアントのセッション管理を見直す。接続終了処理とテスト用モックへの影響を確認してから実施する。

## 実施ルール

- 各段階で、先に仕様を表すテストを追加する。
- テストが未実装状態で失敗することを確認してから実装する。
- 通常時の仕様、通知文、実行時刻、環境変数の意味、外部APIへの書き込み内容を変更しない。
- 異常系の例外型や発生時点を変更する場合は、独断で変更せず、事前に確認する。
- 外部APIへの書き込みを検証する場合は、書き込み後に再取得して保存内容を確認する。
- 仕様変更が発生した場合は、実装前に仕様書を更新する。

## 現時点での振る舞い確認

第1段階・第2段階で通常時の機能フローは維持するよう実装した。ただし、以下は完全同一性をまだ確認していない。

- 不正な環境変数に対する例外の種類と発生タイミング
- import時に起動していた従来動作と、明示的な起動時だけ起動する現在の動作の差
- `AppConfig`導入前後の全設定項目についての境界値・異常値比較

## 主要段階完了後の残作業

主要なリファクタリング段階は完了した。以下は仕上げとして残っている作業である。

### アプリケーションライフサイクル

- `main.py`のグローバル状態を減らす。
- 日記・リンク警告でもアプリケーション全体の共有HTTPセッションを利用する。
- Webサーバースレッドの終了処理を追加する。

### 重複と互換層の整理

- `check_link_warnings.py`と本体の設定・通信処理を共通化する。
- 不要になった互換用関数や重複処理を整理する。
- 型注釈、命名、モジュール境界を統一する。

### 最終確認

- リファクタリング前後の通知文、例外条件、呼び出し順を差分レビューする。
- DNS復旧後に外部ライブテスト7件を実行する。
- 実行環境に必要な依存関係を確認したうえで、実プロセス起動を確認する。
- 必要に応じてテストカバレッジを計測する。

## 残作業の完了条件

- 仕上げ対象のコード変更に対応するテストを先に追加する。
- 通常テストが全件成功する。
- 外部ライブテストは、接続できない場合は未確認として記録する。
- 作業ログに変更内容、確認結果、未完了事項を記録する。
